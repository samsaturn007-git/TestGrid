# ADR-005: Artifact storage and retrieval: a server-keyed store behind an interface, uploads under the lease, signed links to read

**Date:** 2026-11-23 | **Status:** Proposed (PRD-06; accepted at the developer's PRD-06 review)

## Context
- PRD-06 adds screenshots, Playwright traces and log tails per attempt. ARCHITECTURE §12 requires an ADR when the artifact store changes, and this is the first one.
- The bytes come from the worker, which runs browser code against the demo shop. Treat them as untrusted input: a wrong size, a wrong type or a crafted name must never write outside the store or fill the disk.
- The public API has no user authentication until PRD-12, but an artifact UUID that leaks (through a log or a shared URL) must not be enough to read the bytes forever (threat model: "Unauthorised artifact read", ART-003).
- PRD-06 FR-1 says artifacts are uploaded "after the case results are reported and before the attempt completes". In this codebase case results are written only inside the completion transaction (contracts §3), which also ends the attempt. Those two moments are the same call, so the ordering needs a ruling (CONFLICT_REGISTER N20).

## Options considered
- **Where the bytes live**
  - **A. `ArtifactStore` interface; local filesystem by default, optional S3-compatible adapter (chosen).** The database row is the source of truth and the store is just bytes under a key the server generates. Tests run without a network. S3 can be added later without touching callers.
  - B. Bytes in PostgreSQL (`bytea` or large objects). Rejected: 50 MB traces would bloat backups and WAL and compete with the run tables for the 512 MiB database budget (VERSIONS §3).
  - C. Worker writes to a shared volume and the API only records the path. Rejected: the worker would choose paths, the API couldn't check sizes or types, and both containers would need write access to the same volume.
- **When the worker uploads**
  - **A. Before `complete`, while the lease is held (chosen).** The attempt is still `RUNNING`, so the upload is authenticated by the same service token plus lease token as start, heartbeat and complete, and a zombie worker's upload gets `410 lease-expired`. Each upload names its `caseKey` (checked against the claimed keys); the completion transaction links the rows to the `case_results` it inserts.
  - B. After `complete`, inside a grace window. Rejected: it needs a second credential or rule for a terminal attempt, and the target would show as finished while its evidence is still arriving.
- **How the dashboard reads bytes**
  - **A. `GET /artifacts/{id}/content` only with a valid HMAC-signed `expires` + `sig` query, issued by `POST /artifacts/{id}/links`, at most 5 minutes (chosen).** It works in `<img src>` and in a plain download link, and a leaked URL stops working after 5 minutes.
  - B. Serve content to anyone who knows the UUID. Rejected: it fails ART-003 ("unsigned link denied").

## Decision
- `ArtifactStore`: `put(stream, meta) → key`, `open(key)`, `delete(key)`, `exists(key)`, plus a key listing used only by the orphan sweeper.
- `LocalFsArtifactStore`
  - Keys are generated by the server as `yyyy/mm/dd/<uuid>.<ext>` (date in UTC, `ext` from the kind: `png`, `zip`, `log`). Every key is checked against that exact pattern before use, so `..`, `/`, a backslash or a NUL can't reach a path.
  - The resolved path must stay under the real root, and no component of it may be a symbolic link (checked with `NOFOLLOW_LINKS`). Files are opened with `NOFOLLOW_LINKS`.
  - `put` streams into a temporary file inside the root (same filesystem), then makes it visible with an atomic move. Every failure (size, type, I/O) deletes the temporary file, so no partial file is left behind.
- Upload validation happens while streaming: a per-kind byte limit (screenshot 5 MB, trace 50 MB, log 1 MB), magic bytes (PNG signature, ZIP local-file header, valid UTF-8 for logs) and sha256. Violations answer `413 artifact-too-large` or `415 unsupported-media-type`. The worker never chooses a name, a path or a MIME type; the API records the MIME type for the kind.
- Signed links: HMAC-SHA256 over `artifactId`, `expires` (epoch seconds) and a version tag, with the key from `TESTGRID_ARTIFACT_LINK_KEY` (at least 32 characters, required when artifacts are enabled), compared in constant time. The link lasts 300 s or less. Content responses carry `Content-Disposition: attachment`, `X-Content-Type-Options: nosniff`, `Cache-Control: private, no-store` and `Content-Security-Policy: default-src 'none'; img-src 'self'; sandbox`.
- Expiry uses the database clock: `expires_at = now() + retention` (7 days by default, ARCHITECTURE §6). A read of a row that is `EXPIRED` or `PURGED`, or whose `expires_at` has passed, answers `410 artifact-expired`. An unknown id, or a `MISSING` row, answers `404 not-found`.

**What this does NOT claim:**
- That `POST /artifacts/{id}/links` is access control. Until PRD-12 adds user tokens, anyone who can reach the public port can ask for a link. The signature limits how long a leaked URL works, nothing more.
- That the local store survives losing its volume. The orphan sweeper marks rows whose bytes are gone as `MISSING`; it can't recover them.
- That the S3 adapter is production-hardened. If it is built, it is tested against a local S3-compatible container only (Compose profile `s3`).

## Consequences
- The 64 KB JSON body cap (contracts §1) can't apply to the upload path. That path gets its own streaming limits, and only on the internal port.
- The API container needs a writable artifacts volume owned by its non-root user (uid 1000).
- A failed upload never changes a test result. The worker logs an `ARTIFACT_STORE` warning and still completes the attempt.
- Rows and bytes can disagree after a crash between the move and the insert, or after manual deletion. The hourly orphan sweeper reconciles both directions (FR-6).

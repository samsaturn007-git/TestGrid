# API and Data Contracts — v2 (planning baseline)

**Status:** Proposed. This is the single source of truth for the project's vocabulary: statuses, error types, events and table names. PRD-02 publishes `api/openapi.yaml` from the implemented code. Any change to a shape updates this file, the OpenAPI spec, the generated client types and the tests in the same PR (AGENTS.md rule 5).

Each section names the PRD that introduces it. Codex implements only the parts owned by the active PRD.

---

## 1. Conventions

- **Surfaces**
  - `/api/v1/*` is the public API, used by the dashboard, CLI and CI.
  - `/internal/v1/*` is the worker API. It runs on a separate port that is never published on public ingress, and it requires a service token (PRD-03).
- **IDs:** UUID primary keys. `run_events` and `outbox_events` use `bigserial` IDs so they can be ordered and replayed.
- **Time:** `timestamptz` in UTC, ISO-8601 on the wire. Lease and expiry checks always use the database's `now()`, never the worker's clock, which can drift.
- **Errors:** RFC 9457 Problem Details (`application/problem+json`): `type`, `title`, `status`, `detail`, `instance`, `traceId`, `errors[] {field, message}`. The type catalogue is in §6.
- **Pagination**
  - Query: `?limit=1..100` (default 20) `&cursor=<opaque>`.
  - Response: `{ "items": [...], "nextCursor": "..." | null }`.
  - Keyset ordering on `(queued_at DESC, id DESC)`. Offset pagination is not used.
- **Limits:** JSON body ≤ 64 KB, and strings ≤ 200 characters unless a field says otherwise. Unknown JSON fields are rejected on write endpoints.
- **Correlation:** accept and propagate W3C `traceparent`. Every response carries `X-Request-Id`, and every Problem body carries `traceId`.
  - A valid `traceparent` (version `00`, lowercase hex, IDs not all zeros) continues the caller's trace, and its trace ID becomes `traceId`. Anything else starts a new random 32-hex trace.
  - A client's `X-Request-Id` is echoed only if it is 1–64 characters of `A-Z a-z 0-9 . _ -`; otherwise the API generates a UUID.
  - Both IDs are on every API log line (`[traceId requestId]`). Unexpected errors return a generic `500` Problem; exception text and stack traces only go to the log.
- **Spec:** `api/openapi.yaml` (OpenAPI 3.1, generated by springdoc) and `packages/contracts/src/api.ts` (generated by openapi-typescript) are produced from the code by `make contracts`, and `make contracts-check` fails CI when they drift.
  - In responses every field is present; a field that can be empty is `T | null`, never left out. The exception is Problem bodies: `errors` appears only when fields were wrong.
- **Never accepted from clients:** URLs, file paths, repository links, shell fragments, JavaScript, regexes or Playwright CLI flags. Clients choose only from enums and manifest keys.

### 2.2 Target and attempt transitions
| From → To | Trigger | Attempt effect |
|---|---|---|
| `QUEUED → CLAIMED` | claim succeeds | new attempt `CLAIMED`, `attempt_no = previous + 1` |
| `CLAIMED → RUNNING` | worker calls `start` | attempt `RUNNING` |
| `RUNNING → PASSED / FAILED / TIMED_OUT` | `complete` with valid lease | attempt gets the same status |
| `CLAIMED / RUNNING → INFRA_ERROR` | worker reports infra failure, or the final retry is exhausted | attempt `INFRA_ERROR` or `ABANDONED` |
| `CLAIMED / RUNNING → QUEUED` | lease expires and retries remain (reaper) | attempt `ABANDONED` (`LEASE_EXPIRED`); `not_before` set by backoff; `dispatched_at` cleared so the next dispatch has a new generation |
| `QUEUED → QUEUED` | dispatched but unclaimed past the dispatch timeout (reaper, PRD-04) | none; `dispatched_at` cleared for a new generation |
| `QUEUED → INFRA_ERROR` | `max_attempts` dispatches of the target never claimed, in total (reaper, PRD-04) | none (`TARGET_FINISHED` carries `errorClass: WORKER_LOST`) |
| `QUEUED → CANCELLED` | run cancel requested | none |
| `CLAIMED / RUNNING → CANCELLED` | worker sees `cancelRequested` and completes with `CANCELLED`, or the lease expires while a cancel is requested | attempt `CANCELLED` or `ABANDONED` |

Rules:
- **Terminal states never change.** A transition request that arrives late is rejected with a Problem response and logged, never silently applied.
- **Target status is computed by the API from validated case results.** The worker's self-reported status is used only when there are no case results (infra failure, timeout, cancel).
  - Any case `FAILED` → `FAILED`.
  - Otherwise any case `TIMED_OUT` → `TIMED_OUT`.
  - Otherwise every case `PASSED`, `FLAKY` or `SKIPPED` → `PASSED`.
  - Zero cases executed → `INFRA_ERROR` (`CONFIG`).

### 2.3 Run aggregate (truth table, PRD-02 unit test)
- **Not all targets terminal:** the run is `RUNNING` if any target has ever been claimed, otherwise `QUEUED`.
- **All targets terminal:** the run takes the first match in this order: `FAILED > TIMED_OUT > INFRA_ERROR > CANCELLED > PASSED`.
- **Why this order:** a confirmed product failure is the most useful signal. Uncertain outcomes come next. `PASSED` requires every target to pass.
- **"Ever claimed"** means the target has an attempt (`attempt_count > 0`) or is in a status only a claim can reach (`CLAIMED`, `RUNNING`, `PASSED`, `FAILED`, `TIMED_OUT`). `QUEUED`, `INFRA_ERROR` and `CANCELLED` can be reached without a claim, so for those the attempt count decides.
- **Where it lives:** `RunAggregate.of` in the API, a pure function. `GET /runs/{runId}` computes it from the targets on every read. `runs.status` stores the same value for listing and filtering, and every writer that changes a target (PRD-03 onward) must update it in the same transaction.

### 2.4 Quality outcome (PRD-08)
| Situation | Outcome | CLI exit |
|---|---|---|
| Every policy rule satisfied | `PASS` | 0 |
| Any blocking rule violated by test evidence (critical case failed, too many failures, duration regression over limit) | `FAIL` | 1 |
| A required target is missing, `INFRA_ERROR`, `TIMED_OUT` at target level, `CANCELLED`, or the run did not finish before the CLI deadline | `INDETERMINATE` | 2 |
| Bad configuration, authentication or usage | — | 3 |

A failure in a quarantined case does not count toward `FAIL`. It still appears in the rule report as `QUARANTINED_FAIL`.

When rules disagree, the first match wins: any blocking rule `FAIL` → `FAIL`; otherwise any blocking rule `INDETERMINATE` → `INDETERMINATE`; otherwise `PASS`. A confirmed product failure is the more useful signal, as in the run aggregate (§2.3), so a critical failure on chromium with an `INFRA_ERROR` on firefox is `FAIL` (exit 1), never `PASS`. "`TIMED_OUT` at target level" means a target that ended `TIMED_OUT` **without** case results (the whole target timed out); a target that is `TIMED_OUT` because a case timed out has test evidence, and the case counts as a failed case (CONFLICT_REGISTER N37).

**Cancel (PRD-04 FR-8)**
- `POST /runs/{runId}/cancel`, no body. One transaction that locks the run's targets (in id order) and then the run, the same order as claim, complete and the reaper.
- Already terminal: `200` with the run unchanged. The request is still recorded as `RUN_CANCEL_REQUESTED {accepted: false, runStatus}`.
- Otherwise `202` with the run: `cancel_requested_at` is set (kept on a repeat), every `QUEUED` target ends `CANCELLED` (`TARGET_FINISHED` each, dispatched or not), and `RUN_CANCEL_REQUESTED {accepted: true, alreadyRequested, cancelledTargets, activeTargets}` is written. Active attempts see `cancelRequested: true` on their next heartbeat and complete with `CANCELLED`.
- Races resolve by commit order: a completion that commits first keeps its result (the cancel then finds a terminal run, `200`, or leaves that target alone); a claim that commits first gives an active attempt the cancel reaches by heartbeat; a cancel that commits first makes the claim `409 stale-dispatch`. Each target ends in exactly one terminal state.

**Workers (PRD-04 FR-7)**
- `GET /workers`: `{items[{id, name, version, executor, engines, slots, state, startedAt, lastSeenAt, activeAttempts}], globalMaxSessions, activeSessions, dispatchedUnclaimed}`. Live workers first (`ACTIVE`, `DRAINING`), then those `LOST` in the last hour; at most 200. `activeAttempts` counts the worker's `CLAIMED`/`RUNNING` attempts by name (0 for a `LOST` row).

**Read endpoints (PRD-02)**
- **Caller scope:** every endpoint resolves the caller's project in one place (`CallerScope`; today always the local project). A project, suite or run outside that scope answers `404 not-found`, exactly like one that doesn't exist. `POST /projects/{projectId}/runs` applies the same rule.
- **`GET /runs`:** newest first by `(queued_at, id)`. `limit` must be 1–100 (default 20) and anything else is `400 validation-failed`. The cursor is base64url of `v1|<queued_at in epoch microseconds>|<id>`; clients treat it as opaque, and one the API can't parse is `400`. Rows inserted while a client pages land before the first page, so they never cause duplicates or gaps. Items carry `targetCount` and `links.self`.
- **`GET /runs` filters (PRD-05):** `status` (aggregate `RunStatus`) and `trigger` may repeat (or be comma-separated) and match any of their values; `suiteKey` (any revision) and `branch` are exact matches; different filters must all match. An empty value means no filter. `projectId` defaults to the caller's project, and one outside the caller's scope is `404 not-found`. Unknown enum values, a `suiteKey` or `branch` that breaks the create-run rules, and any unknown query parameter (a misspelt filter) are `400 validation-failed`, never ignored. The cursor keeps working under filters; clients send the same filters with it. V5 indexes `(project_id, status, queued_at DESC, id DESC)` and `(project_id, branch, queued_at DESC, id DESC) WHERE branch IS NOT NULL` keep filtered pages an index range scan.
- **`GET /runs/{runId}`:** the run, its targets ordered by `targetKey`, `status` computed as in §2.3, and `links {self, suite}`. Each target carries `latestAttempt` (or `null`): `{id, attemptNo, workerId, status, claimedAt, startedAt, finishedAt, leasedUntil, leaseExpired, lastHeartbeatAt, errorClass}`. `leaseExpired` is `true` when the attempt is still `CLAIMED`/`RUNNING` but `leased_until < now()` (database clock), so a dead worker is visible rather than shown as running (PRD-03 AC-4).
- **`GET /runs/{runId}/results` (PRD-03 FR-9):** `{runId, status, targets[{id, targetKey, engine, status, attempts[{attempt, errorDetail, caseResults[{caseKey, status, durationMs, retryCount, errorClass, errorMessage}]}]}]}`. Attempts are newest first; case results are ordered by `caseKey`. Lease tokens never appear.
- **`GET /capabilities` (PRD-05):** `{"fixturesAllowed": boolean}`. The dashboard shows the fixture-mode controls only when it is `true`; the API still enforces `422 fixture-not-allowed` on its own, so a stale or forged answer changes nothing.
- **`GET /projects`, `GET /projects/{projectId}/suites`, `GET /suites/{suiteId}`:** project, current suites (with `caseCount`), and one suite revision with its cases ordered by `caseKey`. Old revisions stay readable by ID. These lists are bounded by the manifest, so they return one page with `nextCursor: null`.

- **`POST /runs/{runId}/rerun` (PRD-05 FR-6):** body `{scope: FAILED_TARGETS | ALL, idempotencyKey}`, parsed as strictly as create-run (`FAILED_CASES` is `400` until PRD-11). The new run has `trigger: RERUN` and `parentRunId`, and copies the old run's suite revision (`suite_id`), fixture, source and sharding; `FAILED_TARGETS` takes the targets that ended `FAILED`, `TIMED_OUT` or `INFRA_ERROR` (never `PASSED` or `CANCELLED`), `ALL` takes every target. `202` new run, `200` replay with `Idempotent-Replay: true`, `409` key reused with a different request (keys are shared with create-run; the request hash is the canonical `{"rerunOf": <runId>, "scope": <scope>}`). `422 invalid-rerun` when the run has not finished or nothing failed, `422 unknown-suite` when that revision is no longer the current, enabled one, `422 fixture-not-allowed` for a fixture run outside the local profile. A known key is answered before these checks. The new run's `RUN_CREATED` payload adds `parentRunId` and `rerunScope`.
- **`GET /projects/{projectId}/run-counts` (PRD-05):** `{from, to, hours, total, items[{status, count}]}`. A run counts when its `queued_at` is inside the window (database clock), under its current `status`; `items` lists all seven `RunStatus` values in §2.1 order. `hours` outside 1–168 is `400 validation-failed`; a project outside the caller's scope is `404 not-found`.
- **`GET /runs/{runId}/timeline` (PRD-06 FR-7):** `{runId, status, queuedAt, finishedAt, serverNow, heartbeatIntervalSeconds, gapThresholdMs, runEvents[], targets[{id, targetKey, engine, status, events[], attempts[{attempt, heartbeats[], gaps[{from, to, durationMs}], caseResults[], artifacts[], events[]}]}]}`. Events are `{eventId, type, occurredAt, data}`: run events have no target, target events no attempt. Attempts are **oldest first** (the drawing order; `/results` stays newest first). A gap is a silence longer than `gapThresholdMs` = 2 × the heartbeat interval between consecutive signs of life: the claim, the start, each heartbeat, and the end (`finishedAt`, which the reaper sets when it abandons an attempt, or `serverNow` for an attempt still active, so a dead worker's silence keeps growing). Read in one `REPEATABLE READ` snapshot; at most 10,000 events. Same scope rule as `GET /runs/{runId}` (`404`).
- **Retention (PRD-06 FR-6):** a job in the API runs every `testgrid.artifacts.purge-interval` (1 h; first pass 1 min after start). It moves `AVAILABLE` rows past `expires_at` to `EXPIRED`, deletes their bytes, and only then marks them `PURGED` (a failed delete leaves the row `EXPIRED` and is retried next pass; reads already answer `410`). It deletes store files that have no row once they are older than `testgrid.artifacts.orphan-grace` (1 h, at least 5 min, because an upload's file exists briefly before its row), marks `AVAILABLE` rows whose file is gone `MISSING` (reads answer `404`), and removes partial uploads older than the grace. Rows are never deleted. Every age uses the database clock; V10 indexes `artifacts(id) WHERE state = 'EXPIRED'`.
- **`GET /runs/{runId}/results` (PRD-06 additions):** each attempt also carries `artifacts[]` (the `GET /artifacts/{id}` shape, effective state) and each case result `startOffsetMs` (or `null`).
- **`GET /runs/{runId}/results` (PRD-07 additions):** each case result also carries `fingerprintId`, the failure group it belongs to (`null` for passes and skips). Each attempt carries `fingerprintId` for an attempt-level failure (CONFLICT_REGISTER N25), else `null`.
- **Artifacts (PRD-06 FR-4, ADR-005):**
  - `GET /artifacts/{artifactId}`: `{id, attemptId, caseKey | null, kind, mime, byteSize, sha256, state, expiresAt, createdAt}`. `state` reads `EXPIRED` once `expires_at` has passed (database clock), even before the hourly purge marks the row, so the UI can explain it. The storage key is never returned. Unknown, or outside the caller's project: `404 not-found`.
  - `POST /artifacts/{artifactId}/links` (no body): `200 {url, expiresAt}`. `url` is relative to the API origin, `/api/v1/artifacts/{id}/content?expires=<epoch s>&sig=<43 base64url>`, where `sig = HMAC-SHA256(TESTGRID_ARTIFACT_LINK_KEY, "v1:<artifactId>:<expires>")` and `expires` is the database clock + 300 s (`testgrid.artifacts.link-ttl-seconds`, at most 300). `404` unknown or `MISSING`; `410 artifact-expired` for `EXPIRED`, `PURGED` or past `expires_at`. Not access control: until PRD-12 anyone who reaches the public port can ask for a link.
  - `GET /artifacts/{artifactId}/content?expires=&sig=`: the only way to read the bytes. Checks, in order: unknown query parameter `400`; missing, malformed, forged or moved signature `403 forbidden`, decided before any lookup; link expired, or claiming more than 300 s, `403`; then `404` / `410` as for links; bytes gone from the store `404`. `200` streams the bytes with the stored `Content-Type`, `Content-Length`, `Content-Disposition: attachment; filename="<kind>-<id>.<ext>"` (so `npx playwright show-trace trace-<id>.zip` works on the download), `X-Content-Type-Options: nosniff`, `Content-Security-Policy: default-src 'none'; img-src 'self'; sandbox`, `Cache-Control: private, no-store`, `Cross-Origin-Resource-Policy: same-origin`, `Referrer-Policy: no-referrer` and `X-Artifact-Sha256`. An `<img>` still shows a screenshot; navigating to the URL downloads it. Not served on the internal port.
- **Failure groups (PRD-07 FR-2, FR-3, FR-7):**
  - `GET /failure-groups`:
    - **Order:** most occurrences first, by `(occurrence_count DESC, id DESC)`; V13 indexes `failure_fingerprints(project_id, occurrence_count DESC, id DESC)`.
    - **Paging:** the cursor is base64url of `v1|<count>|<id>`. Counts only grow, so a group that gains occurrences while a client pages can move ahead of the cursor. Pages never repeat a row.
    - **Filters:**
      - `projectId` defaults to the caller's project; one outside it is `404`.
      - `category` matches the shown category (the override, else the rule's) and may repeat or be comma-separated.
      - `engine` keeps groups with an occurrence on that engine.
      - `from` (inclusive) and `to` (exclusive) are ISO-8601 instants bounding `lastSeenAt`, with `from < to`.
      - `limit` is 1–100, default 20.
      - An unknown or repeated parameter, a bad value or a bad cursor is `400 validation-failed`.
    - **Items:** `{id, algoVersion, fingerprint, errorClass, category, ruleCategory, ruleId, confidence, overridden, normalisedMessage, occurrenceCount, runCount, engines[], caseKeys[], wholeTarget, firstSeenAt, lastSeenAt, links {self}}`. `caseKeys` are the distinct case-level occurrences, and `wholeTarget` is true when an attempt-level occurrence exists (N25). A second query over the page's ids gathers engines, cases and runs.
  - Each detail occurrence also carries `artifacts[]` (the `GET /artifacts/{id}` shape, effective state): the case's screenshot and trace plus the attempt's log, or the log alone for an attempt-level occurrence. One query covers the whole page of occurrences. The bytes are only ever reached through `POST /artifacts/{id}/links`.
  - The dashboard pages are `/failures` (with filters in the address) and `/failures/{id}`, which shows the rule explanation, the occurrences, the override form and the audit history. The compare page links each row that has a head fingerprint to its group.
  - `GET /failure-groups/{id}`: `{id, algoVersion, fingerprint, errorClass, category, ruleCategory, ruleId, confidence, normalisedMessage, occurrenceCount, firstSeenAt, lastSeenAt, override, evidence, occurrences[], audit[]}`. `category` is what to show: `override.category` when there is an override, otherwise `ruleCategory`. `override` is `{category, reason, by, at}` or `null`. `evidence` is `{ruleId, ruleName, category, explanation, facts {errorClass, occurrences, attempts, runs, engines, passedOnRetry, statusesSeen}, rulesTried[{ruleId, name, category, matched, reason}], confidence {base, occurrenceBonus, agreement, disagreementPenalty, floor, cap, value}}`: every rule tried in order, why each earlier one missed, and the confidence arithmetic. `occurrences` are newest first, at most 50 (`occurrenceCount` is the total): `{runId, targetId, attemptId, attemptNo, engine, suiteKey, caseKey | null, status, errorMessage | null, occurredAt}`, where an attempt-level failure has `caseKey: null` and the attempt's status. `audit` is oldest first, at most 100: `{id, actor, action, occurredAt, metadata}`. Unknown, or outside the caller's project: `404 not-found`.
  - `PUT /failure-groups/{id}/override`: body `{category: FailureCategory, reason}`, parsed strictly (unknown fields, numbers for enums `400`). `reason` is trimmed and redacted and must then be 1–500 characters (`400 validation-failed`). One transaction locks the row, stores `override_*` with `overridden_by = local` and `overridden_at = now()`, and writes `audit_events {actor: local, action: FAILURE_CATEGORY_OVERRIDDEN, object_type: failure_fingerprint, metadata {from, to, ruleId, ruleCategory, confidence, algoVersion, fingerprint, reason}}`. `200` with the group. Sending the override already in place changes nothing and writes no audit row. New occurrences keep relabelling `ruleCategory`, but the override stays in front for this fingerprint (and so this `algo_version`). There is no access control until PRD-12.
- **`GET /cases/{caseKey}/history` (PRD-07 FR-5):** `?suiteKey=` (required), `engine=chromium|firefox|webkit` (optional; without it, every engine the suite allows, in that order), `limit=1..100` (default 20, per engine). A bad key, engine or limit, a repeated parameter, or an unknown one is `400 validation-failed`. A suite with no revision containing the case is `404 not-found`. Response `{caseKey, suiteKey, title, engines[{engine, health | null, results[]}]}`. `health` is the `case_health` row `{label, reason, windowSize, observed, passCount, failCount, flakyCount, flipCount, flipRate, recentOutcomes, computedAt}`, or `null` before the case's first result on that engine. `results` are newest first by when the result was recorded: `{runId, runStatus, trigger, branch, commitSha, targetId, attemptId, attemptNo, status, durationMs, retryCount, errorClass, fingerprintId, finishedAt}`, `SKIPPED` included. One `REPEATABLE READ` snapshot, so the label and the results it was computed from agree. The dashboard page is `/cases/{caseKey}?suiteKey=`, reached from the case drawer.
- **Quality policy (PRD-08 FR-1):**
  - `GET /projects/{projectId}/quality-policy[?version=N]`: `{id, projectId, version, active, createdAt, policy, versions[{id, version, active, createdAt}]}`, the active version unless `version` names a past one; `versions` is newest first, at most 100. `version` must be a positive integer, once; any other parameter is `400 validation-failed`. An unknown version or a project outside the caller's scope is `404 not-found`.
  - `PUT /projects/{projectId}/quality-policy`: body `{reason, policy}`, with `policy` the §12 object **without** `version` (the server assigns it; sending one is an unknown field, `400`). Parsed strictly; every policy field is required. `reason` is trimmed and redacted and must then be 1–500 characters. One transaction takes a per-project advisory lock, deactivates the current version, inserts the next number as active and writes `audit_events {actor: local, action: QUALITY_POLICY_CHANGED, object_type: quality_policy, object_id: <new version's id>, metadata {fromVersion, toVersion, reason}}`. `200` with the new version. Every `PUT` creates a version, even one identical to the current. Runs already evaluated keep theirs. No access control until PRD-12.
- **`GET /runs/{runId}/quality` (PRD-08 FR-2):** `{runId, runStatus, evaluationId, outcome, policy {id, version}, evaluatedAt, rules[]}`. A run is evaluated once, after the transaction that finished it commits, with the policy active at that moment (CONFLICT_REGISTER N35): every `RUN_FINISHED` writer passes through `AttemptRepository.recomputeRun`, which hands the run to the quality loop after commit; a sweep every 5 s (`testgrid.quality.sweep-interval-ms`) evaluates runs finished in the last day that still have none; and this endpoint evaluates a finished run on demand. All three lock the run row, so the first evaluation wins and later ones read it. Before the run finishes, `evaluationId`, `outcome`, `policy` and `evaluatedAt` are `null` and `rules` is empty. A run outside the caller's scope is `404 not-found`.
- **Quarantines (PRD-08 FR-3):**
  - A quarantine is `{id, projectId, caseKey, engine | null, reason, source, createdBy, createdAt, expiresAt, revokedAt | null, state}`. `state` (`QuarantineState`: `ACTIVE`, `EXPIRED`, `REVOKED`) is computed on read from the database clock: `REVOKED` when revoked, else `EXPIRED` once `expires_at` has passed, else `ACTIVE`. Only an `ACTIVE` quarantine excuses failures.
  - `GET /projects/{projectId}/quarantines[?state=]`: `{items[], activeCount, maxActive, autoMode, serverNow, suggestions[]}`. Items are newest first, at most 200; `state` filters (once). `serverNow` is the database clock, for expiry countdowns. `suggestions` (`{suiteKey, caseKey, engine, observed, flakyCount, flipRate, reason}`, most flips first, at most 50) are the `case_health` rows labelled `FLAKY` with no active quarantine covering them, filled only when the policy's `autoMode` is `SUGGEST`. Unknown parameters `400`; a project outside the caller's scope `404`.
  - `POST /projects/{projectId}/quarantines`: body `{caseKey, engine?, reason, expiresAt, source?}`, parsed strictly. `caseKey` must be a case of a current suite (`400` otherwise), `engine` an `Engine` or absent (every engine), `reason` 1–500 after trimming and redaction, `expiresAt` after the database's now and at most 30 days later, `source` `MANUAL` (default) or `SUGGESTED` (`AUTO` is `400`). One transaction takes a per-project advisory lock, then: an active quarantine that already covers the case on that engine (or on every engine) is `409 quarantine-conflict`; `maxActive` active quarantines is `409 quarantine-conflict`. Otherwise `201` with `Location: /api/v1/quarantines/{id}` and an `audit_events {actor: local, action: QUARANTINE_CREATED, object_type: quarantine, metadata {caseKey, engine, source, expiresAt, reason}}` row.
  - `DELETE /quarantines/{id}`: `200` with the quarantine. An `ACTIVE` one becomes `REVOKED` now and writes `QUARANTINE_REVOKED {caseKey, engine}`; one already revoked or expired is returned unchanged with no audit row. `404` unknown or outside the caller's project. Rows are never deleted.
  - **Expiry:** a quarantine stops counting at `expires_at`, whatever any job does. The quality loop's sweep (every 5 s) also records each passed expiry once: it sets `expiry_recorded_at` (`FOR UPDATE SKIP LOCKED`, 100 per pass) and writes `QUARANTINE_EXPIRED {caseKey, engine, expiresAt}` with `actor: system`.
  - **AUTO** (`autoMode: AUTO`): after a run's evaluation is stored, in the same transaction, each `(case, engine)` of that run whose `case_health` label is `FLAKY` with `observed ≥ 10` and no active quarantine gets one: `source: AUTO`, `created_by: system`, `expires_at = now() + 7 days`, reason `AUTO: <health reason> over <n> results`, and a `QUARANTINE_CREATED` audit row carrying `runId`, while `maxActive` allows. It applies to later runs only: the run that triggered it was already judged without it. With `testgrid.case-health.window-size` below 10, AUTO never fires.
  - No access control until PRD-12; `created_by` and audit `actor` are `local`.
- **Rerun link (PRD-05):** `GET /runs/{runId}` carries `parentRunId` (or `null`) and `rerunIds`, the runs that rerun it, oldest first, so the link is visible in both directions. V6 indexes `runs(parent_run_id) WHERE parent_run_id IS NOT NULL`.

**Create-run request**
```json
{
  "suiteKey": "checkout-smoke",
  "targets": [{"executor": "LOCAL", "engine": "chromium"}, {"executor": "LOCAL", "engine": "firefox"}],
  "trigger": "MANUAL",
  "idempotencyKey": "8e1258cb-1d66-4c6d-8eb8-5c28011f202e",
  "fixture": {"mode": "PRODUCT_DEFECT", "seed": 42},
  "sharding": {"mode": "NONE", "shards": 1},
  "source": {"commitSha": "0123456789abcdef", "branch": "main", "ciRef": "gh:123456/1"}
}
```

**Create-run validation (PRD-02)**
- Required: `suiteKey`, `targets` (1–3, no duplicates), `trigger`, `idempotencyKey` (1–200 of `A-Z a-z 0-9 . _ : -`). `fixture`, `sharding` and `source` are optional; `fixture` needs both `mode` and `seed` (0 … 2³¹−1).
- `source.commitSha` is 7–64 lowercase hex, `source.branch` uses git ref characters only (no `:` and no `..`), `source.ciRef` is `<system>:<id>` such as `gh:123456/1`. None of them can hold a URL.
- `400 validation-failed` until their PRDs: `executor: BROWSERSTACK` (PRD-09), `trigger: RERUN` (use the rerun endpoint, PRD-05), any sharding other than `NONE` with 1 shard (PRD-11).
- `422 fixture-not-allowed` when `TESTGRID_PROFILE` is not exactly `local`, or the mode isn't in the suite's `fixtureModes`.
- A body over 64 KB is `400 validation-failed`. JSON is parsed strictly: unknown fields, duplicate keys, strings for numbers and numbers for enums are all rejected.
- A new run gets one target per entry with `target_key = local:<engine>:0`, all `QUEUED`, plus one `RUN_CREATED` event, in one transaction.

**Idempotency**
- `request_hash` is the sha256 of the canonical JSON, with keys sorted and targets sorted, and `idempotencyKey` excluded.
- The insert relies on the unique constraint: `INSERT … ON CONFLICT DO NOTHING`, then `SELECT`.
- Same hash → replay the original run. Different hash → `409`.
- This has to hold when two identical requests arrive concurrently (test API-004).
- Normalisation before hashing (PRD-02): null fields are dropped and `sharding` defaults to `{"mode":"NONE","shards":1}`, so leaving out a default and spelling it out hash the same. Canonical JSON is the §10 form.
- Keys are unique per project. Order of checks: field validation (`400`) first, then the key. A known key is answered before the manifest checks, so a retry still replays after the suite's revision has changed.
- Under concurrency the `INSERT … ON CONFLICT DO NOTHING` waits for the other transaction holding the same key. If it commits, the waiting request reads that run and replays it or returns `409`. If it rolls back, the waiting request inserts its own run.
- Both `202` and the `200` replay carry `Location: /api/v1/runs/{runId}`. A `409` names the existing run in `detail`.

## 5. Events (`run_events` and SSE)

**Event envelope**
```json
{"eventId": 1042, "schemaVersion": 1, "type": "TARGET_CLAIMED", "runId": "…", "targetId": "…", "attemptId": "…", "occurredAt": "2026-11-19T12:00:00Z", "data": {"workerId": "w-1", "attemptNo": 2}}
```

**Event types**
- `RUN_CREATED`, `RUN_CANCEL_REQUESTED`, `RUN_FINISHED`
- `TARGET_DISPATCHED`, `TARGET_CLAIMED`, `TARGET_STARTED`, `TARGET_RETRY_SCHEDULED`, `TARGET_FINISHED`
- `ATTEMPT_ABANDONED`, `CASE_FINISHED`, `ARTIFACT_AVAILABLE`, `QUALITY_EVALUATED`

`ARTIFACT_AVAILABLE` (PRD-06 T2, written by the upload): `{artifactId, kind, caseKey, byteSize}`; `caseKey` is null for a `LOG`.

`QUALITY_EVALUATED` (PRD-08 T1, written with the evaluation, once per run): `{evaluationId, outcome, policyId, policyVersion}`. It comes after `RUN_FINISHED`, in a later transaction.

Payloads written by the reaper (PRD-04 T4):
- `ATTEMPT_ABANDONED`: `{attemptNo, workerId, errorClass: "LEASE_EXPIRED", leasedUntil}`.
- `TARGET_RETRY_SCHEDULED`: `{reason: "LEASE_EXPIRED", attemptNo, nextAttemptNo, maxAttempts, backoffMs, notBefore}` after an abandoned attempt, or `{reason: "DISPATCH_TIMEOUT", dispatchGeneration, dispatchedAt, unclaimedDispatches}` after a lost dispatch.
- `TARGET_FINISHED`: `{status, attemptNo, errorClass}` as for a completion; `attemptNo` is null when no attempt was made.

Clients must ignore event types they don't recognise.

**SSE wire format**
- Each event is sent as `id: <eventId>`, `event: <type>`, `data: <json>`.
- A keep-alive comment `: ping` goes out every 15 s.
- On reconnect the server replays everything after `Last-Event-ID`. If the gap is more than 1,000 events, it sends a single `RESYNC` and the client refetches the full snapshot.
- **Stream rules (PRD-05 T5):**
  - Without `Last-Event-ID` (a first connection, or a new `EventSource` after a fallback) the stream starts with one `RESYNC` whose `id:` is the run's newest event id and whose data is `{runId, eventId}`; history is not replayed, because the client loads the snapshot. Every later event streams live. `RESYNC` always carries an `id:`, so the next automatic reconnect resumes after it.
  - `data:` is the envelope above; `event:` is its `type`. Rolled-back events never appear: an `AFTER INSERT` trigger on `run_events` (V7) calls `pg_notify('run_events', '<run_id>:<id>')`, which is delivered only when the inserting transaction commits.
  - The notification is only a wake-up. A stream remembers the last id it sent and always reads `run_events WHERE run_id = ? AND id > last ORDER BY id`, so events are never dropped, repeated or reordered; each 15 s ping also re-reads, so a lost notification delays an event by at most one ping.
  - `Last-Event-ID` that is not a non-negative integer is `400 validation-failed`. A run outside the caller's scope is `404 not-found` before any stream opens. More than `testgrid.sse.max-streams` (default 100) open streams is `429 rate-limited` with `Retry-After: 5`. A stream closes after 30 minutes and `EventSource` reconnects with `Last-Event-ID`.
  - The response carries `X-Accel-Buffering: no` so the nginx proxy does not buffer it.

**Artifact upload (PRD-06 FR-1/FR-3, ADR-005)**
- Query: `kind` (`SCREENSHOT`, `TRACE` or `LOG`) and `caseKey`, each at most once; any other parameter is `400 validation-failed`. `SCREENSHOT` and `TRACE` need a `caseKey` of the claimed suite revision; `LOG` (the attempt's worker log tail) takes none.
- Header `X-TestGrid-Lease-Token: <leaseToken>` (never in the URL). The lease is checked like `heartbeat`: unknown attempt `404`, wrong token or expired lease `410 lease-expired`, finished attempt `409 attempt-not-active`. The worker uploads **before** `complete`, while it holds the lease (CONFLICT_REGISTER N20).
- Body: `multipart/form-data` with exactly one part, `name="file"`; anything else is `415` (content type) or `400` (framing). The part's own `Content-Type` is ignored.
- Limits per kind: screenshot 5 MB, trace 50 MB, log 1 MB (`413 artifact-too-large`, from `Content-Length` before reading or while streaming). Magic bytes: PNG signature, ZIP local file header, UTF-8 text without NUL; an empty file is `415`. At most 20 artifacts and 200 MB per attempt (`413`). This path is the only one exempt from the 64 KB body cap (CONFLICT_REGISTER N21).
- The API streams the part into the store and computes sha256 on the way; no database lock is held meanwhile. Any violation, or a lease lost before the row is written, leaves no file behind.
- What the worker sends (PRD-06 FR-1): nothing for a fully passing attempt. Otherwise the log tail (the Playwright process's stdout and stderr, redacted as above, colour codes and NUL removed, last 256 KB), then the screenshot and trace of each `FAILED`, `TIMED_OUT` or `FLAKY` case (the last try of a failure, the first failed try of a flake). Files are read only if they are regular files inside the attempt's output directory. A trace that contains any secret value, or that can't be read completely, is withheld (CONFLICT_REGISTER N22). A failed or refused upload is logged as an `ARTIFACT_STORE` warning and never changes the completion.
- `201` with `Location: /api/v1/artifacts/{id}` and `{id, attemptId, caseKey, kind, mime, byteSize, sha256, state, expiresAt, createdAt}`; the storage key never leaves the server. Writes `ARTIFACT_AVAILABLE`.

**Access (PRD-03 FR-2)**
- The worker API listens on its own port (`TESTGRID_INTERNAL_PORT`, default 8081), opened only when `TESTGRID_WORKER_TOKEN` (≥ 32 characters) is set. Compose never publishes it.
- Every call sends `Authorization: Bearer <TESTGRID_WORKER_TOKEN>`; the API compares sha256 hashes in constant time. Missing or wrong → `401 unauthorized`.
- `/internal/*` on the public port, and any other path on the internal port, is `404 not-found`, the same answer as a path that doesn't exist.

**Check order for start, heartbeat and complete** (all inside one transaction that locks the attempt and its target; the lease is checked against the database's `now()`):
1. Unknown attempt → `404`.
2. Lease token doesn't match the attempt's hash → `410 lease-expired`.
3. Attempt already terminal:
   - complete with the attempt's own `completionKey` → `200`, `Idempotent-Replay: true`, the stored outcome, nothing written;
   - attempt `ABANDONED` (lease lost) → `410 lease-expired`;
   - complete with another key → `409 idempotency-conflict`; start or heartbeat → `409 attempt-not-active`.
4. `leased_until <= now()` → `410 lease-expired`.
5. Complete only: a payload that doesn't fit the claim → `422 invalid-completion`, nothing written.

A repeated `start` by the lease holder is answered `200` without a second transition.

**Claim (PRD-04 FR-5)**
- PRD-03's `POST /claims/next` was removed in PRD-04 T3 (CONFLICT_REGISTER N11). Every claim names the target of a dispatch message and the message's `dispatchGeneration`, so no claim can skip the dispatcher's order or cap.
- One transaction:
  1. Take the dispatcher's advisory lock, so claims and dispatch ticks count capacity one at a time.
  2. Lock the target row (no `SKIP LOCKED`: a duplicate delivery waits, then sees the claim). Unknown target → `404`.
  3. `409 stale-dispatch` when the message is no longer the current dispatch: the target is already `CLAIMED`/`RUNNING` or terminal; `dispatchGeneration` differs from the target's; the target was requeued and is not dispatched (`dispatched_at` is null); or the run has a cancel request.
  4. `429 capacity-exhausted` when active attempts (`CLAIMED`/`RUNNING`) already equal `global_max_sessions`. A claim normally can't hit this, because the target was counted as dispatched-but-unclaimed; it happens when the cap was lowered after dispatch.
  5. Insert the attempt, set the target `CLAIMED`, write `TARGET_CLAIMED` with `{workerId, attemptNo, messageId, dispatchGeneration}`.
- Nothing is written on `404`, `409` or `429`.

**Worker registry (PRD-04 FR-7)**
- `name` is what the worker's claims record as `workerId` (`^[A-Za-z0-9._-]{1,64}$`; Compose gives each container `worker-<hostname>`). `version` matches `^[A-Za-z0-9._+-]{1,64}$`; `slots` is 1–16.
- Registering under a name that has a live row (the container restarted) marks that row `LOST` and inserts a new one; a `LOST` row is never revived.
- The worker registers before it consumes, heartbeats every `heartbeatIntervalSeconds`, and on `410` registers again. On `SIGTERM` it calls `drain` and then stops consuming.
- The reaper marks a live worker not heard from for 3 × `lease_ttl_s` `LOST`. A drained worker that exits stays `DRAINING` until then.
- Claims and leases don't depend on the registry: the lease protocol already fences a dead worker.

**Claim response**
```json
{"attemptId": "…", "attemptNo": 1, "runId": "…", "targetId": "…", "leaseToken": "<opaque, 32 random bytes, base64url>", "leaseTtlSeconds": 30,
 "heartbeatIntervalSeconds": 10, "suite": {"suiteKey": "checkout-smoke", "revision": "a1b2c3d4e5f6"},
 "engine": "chromium", "caseKeys": ["cart-total", "checkout-happy-path"], "fixture": {"mode": "PASS", "seed": 42}, "timeoutMs": 120000}
```

**Completion request**
```json
{"leaseToken": "…", "completionKey": "attempt-<id>-final", "status": "COMPLETED_WITH_RESULTS",
 "caseResults": [{"caseKey": "cart-total", "status": "FAILED", "durationMs": 2912, "retryCount": 0,
   "errorClass": "ASSERTION", "errorMessage": "Expected total 59.97, received 61.97"}],
 "workerError": null}
```
- `status` is `COMPLETED_WITH_RESULTS`, `INFRA_ERROR`, `TIMED_OUT` or `CANCELLED`.
- Each case result may carry `startOffsetMs` (PRD-06 FR-7): ms after the attempt's first case started, from Playwright's report. Optional and nullable; when present it is 0 … the suite timeout plus the grace period (`422` otherwise, `400` if negative). Offsets, not timestamps, so the worker's clock never enters the database.
- Each case result may carry `errorFrames` (PRD-07 FR-1, CONFLICT_REGISTER N24): at most 3 of the failure's top stack frames, innermost first, as `file:function`. The file is relative to the worker root; frames under `node_modules`, `node:` or outside the root are skipped. There is never a line number, and an anonymous function is `<anonymous>`. Each frame must match `^(?!/)(?!(?:.*/)?\.\.(?:/|:))[A-Za-z0-9._/-]{1,160}:[A-Za-z_$<][A-Za-z0-9_$.<>-]{0,79}$` (`400` otherwise: absolute path, `..`, a line number, `|` or `;`). Optional; absent, `null` and `[]` all mean none. Frames need an `errorClass`, and a `PASSED` or `SKIPPED` case carries none (`422`).
- The API checks the case keys against the claimed `caseKeys` and rejects any unknown, missing or duplicate key with `422`.
- Durations must be between 0 and the suite timeout plus a grace period (60 s).
- `COMPLETED_WITH_RESULTS`: exactly one result per claimed case and `workerError: null`. `errorClass` is required for `FAILED` and `TIMED_OUT`, and `PASSED` / `SKIPPED` carry no error. `retryCount` is 0 … the suite's `playwrightRetries`, and `FLAKY` needs at least 1. The target status is computed from these results (§2.2); the worker's opinion is not asked.
- `INFRA_ERROR`, `TIMED_OUT`, `CANCELLED`: `caseResults: []`. `INFRA_ERROR` needs `workerError {errorClass, message}`; `TIMED_OUT` defaults to `TEST_TIMEOUT`; `CANCELLED` is accepted only when the run has a cancel request.
- Error messages are redacted before they are stored, by the worker and again by the API (PRD-06 FR-5): the values of `Authorization`, `Proxy-Authorization`, `Cookie` and `Set-Cookie` headers, bearer tokens, JWT-shaped strings, long opaque strings (40+ characters), and the value of every environment variable named `*_TOKEN`, `*_KEY`, `*_SECRET` or `*_PASSWORD` (8+ characters, the AC-4 canary included) are masked as `[REDACTED]`; control characters are removed; ≤ 2,000 characters.
- Response `200 {attemptId, attemptStatus, errorClass, targetId, targetStatus, runId, runStatus}`; a replay returns the same body.
- Lease tokens are stored only as a sha256 hash, compared in constant time, and never logged.

## 8. Run comparison (PRD-07)

`GET /runs/compare?base=<runId>&head=<runId>` compares two runs of the same suite key. The revisions may differ; the response notes when they do.

Each `(caseKey, engine)` pair gets one of:

| Category | Meaning |
|---|---|
| `NEW_FAILURE` | passed in base, failed in head |
| `FIXED` | failed in base, passed in head |
| `STILL_FAILING` | failed in both. `fingerprintChanged` is true if the failure signature differs |
| `STILL_PASSING` | passed in both |
| `FLAKY_IN_HEAD` | `FLAKY` status or `case_health` label `FLAKY` |
| `ADDED` / `REMOVED` | case exists in only one run |
| `NOT_COMPARABLE` | target missing or `INFRA_ERROR` on either side |

- **Duration regression:** the head duration is more than `base × 1.5` and also more than `base + 500 ms`. Both comparisons are strict, and both thresholds are configurable (`testgrid.compare.regression-ratio`, `testgrid.compare.regression-min-delta-ms`). It is flagged on any row where both sides ran, whatever the category.
- **Shortcut:** `?base=last-green&head=<runId>` finds the most recent `PASSED` run on the same branch and suite. That means the newest run by `(queued_at, id)` that was queued before head, with `status = PASSED`, the same suite key (any revision) and the same branch. A head with no branch matches runs with no branch. If there is none, `404 not-found` says so.

**Implementation (PRD-07 T4).** `RunComparison` (pure) and `RunComparisonService` read one `REPEATABLE READ` snapshot.
- **What each side is:** a run's side is its suite revision's case keys, plus each engine's target. A target has results when it finished `PASSED`, `FAILED` or `TIMED_OUT`. Its results are the case results of its newest attempt that has any. One target per engine until PRD-11; shards' results will merge per engine.
- **The algorithm:** each side is indexed once into a hash map keyed by `(caseKey, engine)`, and every key of the union is looked up in both. That is O(n) in the results; the display sort is O(n log n) over the rows.
- **Category for each key**, first match:
  1. `ADDED` if the base revision lacks the case (only for engines head ran); `REMOVED` if the head revision lacks it (only for engines base ran).
  2. `NOT_COMPARABLE`, with a reason, when either side has no target for the engine, the target has no results (`INFRA_ERROR`, `CANCELLED`, unfinished), the case has no result, or it was `SKIPPED`.
  3. `FLAKY_IN_HEAD` when head's status is `FLAKY`, or the case's **current** `case_health` label on that engine is `FLAKY` (so runs after head count too).
  4. Otherwise by pass (`PASSED`, `FLAKY`) and fail (`FAILED`, `TIMED_OUT`): `NEW_FAILURE`, `FIXED`, `STILL_FAILING` (with `fingerprintChanged` when both fingerprints exist and differ) or `STILL_PASSING`.
- **Response:** `{base, head, baseIsLastGreen, sameRevision, thresholds {regressionRatio, regressionMinDeltaMs}, counts[{category, count}] (every category, in the order above, zeros included), durationRegressions, rows[{caseKey, engine, category, baseStatus, headStatus, baseDurationMs, headDurationMs, durationRegression, baseFingerprintId, headFingerprintId, fingerprintChanged, headHealthLabel, reason}]}`. `base` and `head` are `{id, status, suiteKey, revision, branch, commitSha, fixtureMode, fixtureSeed, trigger, queuedAt, finishedAt}`. Rows are sorted by category (in that order), then case, then engine.
- **Parameters:** `base` is a run ID or `last-green`, and `head` is a run ID (lowercase UUIDs). Both are required, each once; anything else is `400 validation-failed`. A run outside the caller's project is `404`.
- **UI:** the dashboard page is `/compare?base=&head=`, reached from the run page's "Compare with last green" link.

### 8.1 Failure fingerprint `fp_v1` (PRD-07 FR-1)

`dev.testgrid.api.failure.FingerprintV1`, computed by the API from what the worker sent. Pure, so a future `fp_v2` can sit beside it; fingerprints are stored with their `algo_version` and only compared within one version.

**Normalisation `n(message)`.** One pass applies, in this order:
1. Strip ANSI escape sequences (CSI and OSC), then every control character except `\n` and `\t`.
2. Cut everything from the first line that starts with `Call log:` (Playwright's call log grows with timing, for example `14 × locator resolved`).
3. Drop URL query strings: `scheme://host/path?query` keeps `scheme://host/path` (a `#fragment` stays). The query ends at whitespace, `#`, a quote, `<`, `>` or `)`, so `(…/x.png?sig=1)` keeps its closing bracket.
4. UUIDs → `<UUID>`.
5. Timestamps → `<TS>`: ISO-8601 date-times (with `T` or a space, optional seconds, fraction and `Z`/offset) and bare `HH:MM:SS[.fff]` times.
6. Temporary paths → `<TMP>`: `/tmp/…`, `[/private]/var/folders/…`, `X:\…\Temp\…` and Playwright's `test-results/…`.
7. Hex → `<HEX>`: `0x…`, and bare runs of 8 or more hex characters with at least one digit and one letter (commit and run IDs; words like `deadbeefcafe` stay).
8. Each remaining run of digits → `<N>`.
9. Runs of spaces and tabs become one space, blank lines and spaces around line breaks are removed, and the text is trimmed.

The pass repeats until the text stops changing, so `n(n(x)) = n(x)` holds by construction. A placeholder can create a new word boundary, so one pass alone would not guarantee it. The loop always ends: no rule adds a digit, `/` or tab, and every change removes one of them or shortens the text.

**Fingerprint.** `sha256("fp_v1|" + errorClass + "|" + frames.join(";") + "|" + n(message))`, first 16 lowercase hex characters (64 bits). Frames can't contain `|` or `;` and the error class is an enum, so the free-text message, which comes last, can't shift a field boundary. Only the first 3 frames count. The value for the recorded `PRODUCT_DEFECT` failure (`ASSERTION`, frame `suites/checkout-smoke.spec.ts:<anonymous>`) is pinned in `FingerprintV1Test` as `31e12582bd8cb543`: a change to any rule changes it, and that means `fp_v2`.

**Input.** The message is the redacted one the API stores, with redaction before normalisation, so a secret is masked before its digits become `<N>` and never reaches `sample_message` in pieces. The redactor removes the ESC character but leaves the rest of a colour code (`[31m`), so the completion path (PRD-07 T2) calls `FingerprintV1.stripAnsi` before it redacts. The worker already sends messages without colours.

### 8.2 Failure classifier (PRD-07 FR-2)

The rule table is `api/src/main/resources/failure-rules.yaml`, loaded at startup. An invalid table stops the API: unknown fields or values, no catch-all last rule, a base above the cap, or a `PRODUCT_SUSPECTED` alternative that does not require `errorClassIn: [ASSERTION]`. That last check is AC-2 as a property of the table itself: an infrastructure fault can't reach a product label.

**When.** The completion transaction does this, after the run lock (§7 lock order):
1. Fingerprint each `FAILED`, `TIMED_OUT` or `FLAKY` case that has an error class. Without case results, fingerprint the `INFRA_ERROR` or `TIMED_OUT` attempt itself (from its `workerError`, no frames; N25).
2. Upsert each group in fingerprint order (`INSERT … ON CONFLICT DO UPDATE occurrence_count + n`), which locks its row. Two completions of different runs therefore can't deadlock.
3. Link the case results (or the attempt).
4. Once the attempt is final, relabel every group it touched from that group's facts.
5. The labels commit with the results.

Occurrences that the reaper abandons (`LEASE_EXPIRED`, `WORKER_LOST` without a completion) are not grouped.

**Facts** (over all the group's occurrences): `errorClass`, `occurrences`, distinct `attempts`, `runs`, `engines`, `passedOnRetry` (status `FLAKY`), `statusesSeen`, `casesLabelledFlaky`.

**Rules** (first match wins):

| Rule | Matches | Category | Base |
|---|---|---|---|
| R1 `selector-not-found` | error class `SELECTOR_NOT_FOUND` | `TEST_BROKEN` | 0.80 |
| R2 `test-timeout` | error class `TEST_TIMEOUT`, or any occurrence `TIMED_OUT` | `TIMEOUT` | 0.85 |
| R3 `environment` | `BROWSER_LAUNCH`, `WORKER_LOST` or `NETWORK` | `ENVIRONMENT` | 0.85 |
| R4 `assertion-passed-on-retry` | `ASSERTION` and ≥ 1 occurrence passed on a retry | `AUTOMATION_FLAKE` | 0.60 |
| R5 `assertion-reproduced` | `ASSERTION` in ≥ 2 distinct attempts (any runs) | `PRODUCT_SUSPECTED` | 0.70 |
| R6 `no-rule-matched` | anything | `UNKNOWN` | 0.30 |

R4 also matches when `case_health` labels one of the group's cases `FLAKY` (fact `casesLabelledFlaky`, condition `caseHealthFlaky: true`). That evidence is weaker than a retry, so its agreement, and with it the confidence, is lower. The completion updates `case_health` (§8.3) before it relabels, so the label it reads includes this result. A group is only relabelled when it gets a new occurrence; a later change to a case's label alone doesn't relabel it.

**Confidence** = `base + 0.02 × min(occurrences − 1, 5) − 0.30 × (1 − agreement)`, each part rounded to 0.01 and the sum kept within 0.05 … 0.95. `agreement` is the share of occurrences that fit the rule: those that did not pass on a retry, except for R4, where it is those that did. Examples: `PRODUCT_DEFECT` seen in 3 attempts gives 0.70 + 0.04 − 0 = 0.74. A selector failure that passed on a retry in 9 of 10 occurrences gives 0.80 + 0.10 − 0.27 = 0.63. The label is "likely", never proof: the UI shows the rule, its facts and this arithmetic.

### 8.3 Case health (PRD-07 FR-4)

A rolling window of a case's last `testgrid.case-health.window-size` (20, 5–100) outcomes on one engine, per `(project, suite_key, case_key, engine)`. `SKIPPED` is not an outcome.

- **Update:** the completion transaction appends each case's outcome to its row and recomputes it ("incrementally on `TARGET_FINISHED`"). This is O(N) on the stored `recent_outcomes`, with no history read. Rows are locked in key order after the failure-group rows, so completions can't deadlock. A smaller window after a restart applies on each case's next result; a larger one fills up as results arrive.
- **`flip_rate`** = transitions / (n − 1), where a transition is a pass (`P`, `K`) next to a failure (`F`, `T`). It is 0 when n < 2.
- **Label**, first match:
  - `INSUFFICIENT_DATA` when n < `min-observations` (5).
  - `FLAKY` when both outcomes are present and `flip_rate` ≥ `flip-rate-threshold` (0.2, inclusive), or when at least `flaky-statuses` (2) results passed only on a retry.
  - `FAILING` (a case_health label only, CONFLICT_REGISTER N3) when the last `failing-streak` (3) all failed.
  - `STABLE` otherwise.
- **`reason`** says why, for example `5 flips in 5 transitions (1.00 ≥ 0.20)` or `the last 3 results failed`.
- **Known effect:** with few results, one new failure after a pass can reach 0.2. `PPPPPF` is `FLAKY`, and `PPPFFF` is `FLAKY` rather than `FAILING`. Over the full window the same change is `FAILING`. Runs of different fixture modes share one window, so alternating `PASS` and `PRODUCT_DEFECT` runs make `cart-total` `FLAKY`, and its group follows rule R4.

## 9. Messaging (RabbitMQ, PRD-04)

- **Exchange:** `tg.dispatch` (direct, durable).
- **Queues:** quorum queues `tg.targets.<engine>` with routing key `engine.<engine>`.
- **Retry:** `tg.targets.retry` with a per-message TTL and a dead-letter route back to `tg.dispatch`.
- **Dead letters:** exchange `tg.dlx` → queue `tg.targets.dead`.
- **Queue arguments** (declared by the API on every connection; RabbitMQ refuses to change them later, so they are fixed here):
  - `tg.targets.<engine>`: `x-queue-type: quorum`, `x-delivery-limit: 5`, `x-dead-letter-exchange: tg.dlx`.
  - `tg.targets.retry`: `x-queue-type: quorum`, `x-dead-letter-exchange: tg.dispatch` (messages carry their own TTL).
  - `tg.dlx` is a durable fanout exchange; `tg.targets.dead` is a quorum queue bound to it.
- **Message body:** `{messageId, targetId, dispatchGeneration, schemaVersion: 1}`, persistent, with headers `traceparent` and `x-tg-run-id`.
  - AMQP properties: `message_id` = `messageId`, `type` = `TARGET_DISPATCHED`, `content_type` = `application/json`.
  - The body is the `outbox_events.payload` of the dispatch, published unchanged. A redelivered or re-published message has the same `messageId` and `dispatchGeneration`.
- **Publishing (outbox, PRD-04 FR-3):** publisher confirms and the `mandatory` flag. A row is marked published only after an ack with no return; a nack, a return (unroutable), a 5 s confirm timeout or a broken connection leaves it unpublished with `publish_attempts + 1` and `next_attempt_at = now() + 1 s × 2ⁿ⁻¹` after the n-th failure (capped at 30 s).
- **Consumers (worker, PRD-04 T3):** manual acknowledgement with `prefetch = worker slots` on each engine queue the worker serves. Quorum queues have no global QoS, so a worker that serves several engines may hold more deliveries than slots; it runs at most `slots` attempts and the extra deliveries wait unstarted. What happens to a message:

  | Claim or attempt result | Message |
  |---|---|
  | attempt finished: `complete` answered `2xx` (replay included) or `4xx`, the start was refused, the lease was lost, or the completion could not be delivered (the reaper owns recovery) | ack |
  | `claim` `409 stale-dispatch` or `404` | ack |
  | `claim` `429 capacity-exhausted`, `401`/`403`, `5xx` or no answer | retry queue |
  | body not the schema above, or `claim` `400` | `basic.nack` without requeue → `tg.dlx` → `tg.targets.dead` |
  | worker crashes or its channel closes before the ack | the broker redelivers; counts toward `x-delivery-limit` |
  | worker stops (`SIGTERM`) before the message started | `basic.nack` with requeue |

- **Retry publish:** default exchange, routing key `tg.targets.retry`, publisher confirm, then the original is acked. The body, `message_id`, `type` and headers are copied; broker headers (`x-death`, `x-first-death-*`, `x-last-death-*`) are dropped. It adds:
  - `expiration` = 1 s × 2ⁿ⁻¹ for the n-th retry, capped at 30 s, ±20 % jitter;
  - header `x-tg-retries` = n;
  - `CC: engine.<engine>`. When the TTL expires the message is dead-lettered to `tg.dispatch` with its routing keys, and the CC key routes it back to `tg.targets.<engine>` (TopologyTest checks this on RabbitMQ 4.4.1).
  - If the publish isn't confirmed, the original is requeued after 1 s instead of acked. A crash between the confirm and the ack leaves two copies; the claim fences the second.
- **Delivery limit (checked on RabbitMQ 4.4.1):** a redelivery after a consumer dies counts toward `x-delivery-limit: 5`; the first delivery plus five redeliveries, then the message is dead-lettered with reason `delivery_limit`. A `basic.nack` with requeue does **not** count, so the worker uses it only on shutdown.
- **Closing (checked on RabbitMQ 4.4.1):** an ack followed straight by `connection.close()` was lost and the message redelivered (probe from the worker container: 1 message left; closing the channel first: 0). The worker therefore closes its channel, waiting for `close-ok`, before the connection.
- **Dead letters:** `tg.targets.dead` keeps them for an operator (replay runbook: PRD-04 T7). A dead-lettered target stays `QUEUED` and dispatched until the reaper's dispatch timeout (5 min); then it is dispatched again with a new generation, or ends `INFRA_ERROR` (`WORKER_LOST`) once `max_attempts` of its dispatches went unclaimed (counted over the target's whole life, `dispatch_generation − attempt_count`, not consecutively) (ARCHITECTURE §4, CONFLICT_REGISTER N17). The `testgrid_dlq_depth` metric and its alert come with PRD-12 (ARCHITECTURE §8).

## 10. Suite manifest (PRD-01/03)

The manifest lives in `worker/manifest/suites.json` and is validated by a JSON Schema in `packages/contracts`. The API seeds the `suites` and `test_cases` rows from the same file at startup.

```json
{"schemaVersion": 1, "suites": [{
  "suiteKey": "checkout-smoke", "displayName": "Checkout smoke", "specFiles": ["suites/checkout-smoke.spec.ts"],
  "allowedEngines": ["chromium", "firefox", "webkit"], "timeoutMs": 120000, "playwrightRetries": 1,
  "baseUrlRef": "DEMO_SHOP_INTERNAL", "fixtureModes": ["PASS", "PRODUCT_DEFECT", "AUTOMATION_FLAKE", "SELECTOR_DRIFT", "TIMEOUT"],
  "cases": [{"caseKey": "cart-total", "title": "cart total includes tax", "tag": "@cart-total", "critical": true}]
}]}
```

- The JSON Schema is `packages/contracts/schema/suite-manifest.schema.json` (draft 2020-12, unknown fields rejected). Beyond the schema, the API also rejects duplicate `suiteKey` or `caseKey`, a `tag` other than `@<caseKey>`, duplicate JSON keys, and spec files that don't resolve to a regular file under `worker/suites/` (symlinks included).
- `enabled` is optional (default `true`); `expectedDurationMs` per case is optional.
- `baseUrlRef` points to a worker setting that is on an allowlist; the manifest never contains a URL.
- The revision is computed from the spec files and the manifest entry, never typed by hand:
  - Input, as UTF-8: the line `testgrid-suite-revision/v1`, then the canonical JSON of the manifest entry as written (defaults not applied), then for each `specFiles` entry in manifest order its path on one line and the lowercase sha256 hex of its bytes on the next. Every line ends with `\n`.
  - Canonical JSON: object keys sorted by UTF-16 code unit (JavaScript's default sort), array order kept, no whitespace, integers only, strings escaped as `JSON.stringify` does.
  - Revision: the first 12 hex characters of the sha256 of that input. `ManifestLoaderTest.revisionFollowsTheDocumentedAlgorithm` pins it; the PRD-03 worker must reproduce it exactly.
  - Spec files are checked out with LF line endings (`.gitattributes`), so the bytes don't depend on the platform.

## 12. Quality policy schema (PRD-08)

```json
{"version": 3, "requiredTargets": ["local:chromium", "local:firefox"], "failOnCriticalCase": true,
 "maxFailedCases": 0, "failOnInfraError": true, "maxFlakyRate": 0.2,
 "durationRegression": {"enabled": true, "maxRatio": 1.5, "minDeltaMs": 500, "blocking": false},
 "quarantine": {"honor": true, "maxActive": 5, "autoMode": "SUGGEST"}}
```

- `autoMode` is `OFF`, `SUGGEST` or `AUTO`.
- `AUTO` quarantines a case only when it is labelled `FLAKY` with at least 10 observations, and the quarantine expires after 7 days. Every quarantine writes an audit event.
- Each rule in the evaluation result reports `{ruleId, observed, threshold, outcome, blocking, evidence[]}`.

**Fields and limits (PRD-08 T1).** All required. `requiredTargets`: 1–3 distinct `<executor>:<engine>` names, `local:chromium`, `local:firefox` or `local:webkit` (`browserstack:*` from PRD-09). `maxFailedCases` 0–1000. `maxFlakyRate` 0–1. `durationRegression.maxRatio` above 1, at most 10; `minDeltaMs` 0–600000 (they replace `testgrid.compare.*` for the gate). `quarantine.maxActive` 0–50.

**Rules, in report order.** `observed` and `threshold` are numbers, or `null` when nothing was measured. Failed cases are `FAILED` and `TIMED_OUT` results; the results used are each finished target's newest attempt that has any, as in §8.

| `ruleId` | `observed` / `threshold` | Outcome | Blocking |
|---|---|---|---|
| `required-targets` | required targets satisfied / required targets | `INDETERMINATE` unless every required target is satisfied and the run is not `CANCELLED`. A required target (CONFLICT_REGISTER N34) is satisfied when the run has at least one target of that executor and engine and **every** such target (all shards) has test evidence: `PASSED`, `FAILED`, or `TIMED_OUT` with case results | always (invariant I9) |
| `infra-error` | targets that ended `INFRA_ERROR` / 0 | `INDETERMINATE` if any, else `PASS` | `failOnInfraError` |
| `critical-cases` | failed results of cases with `critical: true`, quarantined ones excluded / 0 | `FAIL` if any | `failOnCriticalCase` |
| `max-failed-cases` | failed results, quarantined ones excluded / `maxFailedCases` | `FAIL` when observed **>** threshold (equal passes) | always |
| `max-flaky-rate` | `FLAKY` results (quarantined excluded) ÷ results other than `SKIPPED`, rounded to 4 places for display / `maxFlakyRate` | `FAIL` when the unrounded rate **>** threshold (1/5 against 0.2 passes) | always |
| `duration-regression` | cases slower than the last green run (§8, with the policy's `maxRatio` and `minDeltaMs`), quarantined excluded / 0 | `FAIL` if any. `PASS` with `observed: null` when there is no last green run; `PASS`, `null` / `null`, non-blocking when `enabled` is false | `durationRegression.blocking` |
| `quarantine-honored` | failures an active quarantine excused / `null` | always `PASS`; it lists the `QUARANTINED_FAIL` items so they stay visible. With `honor: false`, quarantines are ignored by every rule and this reports 0 | never |

**Evidence items** are `{target, engine, caseKey, status, counted, detail}`. `target` is the target key, or the policy's `<executor>:<engine>` for a required target the run doesn't have. `status` is the target's or case's status, `QUARANTINED_FAIL` for a failure a quarantine excused, or `null` for a note. `counted` says whether the item counts toward `observed`; `detail` is a readable sentence (error class, durations against the last green run's id, the quarantine's id and expiry). Evidence is bounded by the manifest: at most one item per case and target.

**Quarantines in the evaluation.** The evaluator reads the project's active quarantines in its own transaction (database clock). A quarantine covers a result when the case key matches and its engine is null or the result's engine. With `quarantine.honor: true` a covered failure is excluded from `critical-cases`, `max-failed-cases` and `duration-regression`, and a covered `FLAKY` result from `max-flaky-rate`; each appears in the evidence with `counted: false` (a failure as `QUARANTINED_FAIL`) and the quarantine's id and expiry in `detail`. `quarantine.maxActive` caps active quarantines at creation; it is not re-checked at evaluation.

**Where it lives:** `QualityRules.evaluate` in the API, a pure function of the policy, the run's facts and the active quarantines, unit-tested over the boundaries (`QualityRulesTest`). `QualityEvaluator` collects the facts and stores the result.
